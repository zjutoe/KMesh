### 2. 构造固定候选目录，生成可重建的完整 witness

候选 ID 是操作词，字符顺序固定为 `C,I,J,T`，分别代表 COPY、INV、JOIN、INTER。字符从叶向根执行。先按该字符顺序枚举全部长度 2 的词，再枚举全部长度 3 的词；即 16 + 64 = 80 项。可以使用 `itertools.product`，不按集合迭代次序排序，也不靠运行结果挑选子集。`CC` 是首项，`TTT` 是末项；长短词不能混排。

每个候选重新创建一个互相独立的最小世界：

1. 初始唯一 clause 为事实 `[] -> p0(e0,e1)`，初始 proof 为 `ProofStep(0, (), p0(e0,e1))`；当前根为该 proof 的最后一步。
2. 第 i 个字符中 i 从 1 开始，当前 ground 根记为 `p{i-1}(u,v)`。新 head 谓词总是 `p{i}`。局部变量拼写固定 `?x,?y,?z`，作用域仅该 clause。
3. 按下表追加 clause 及对应 proof。每个新增 clause 都恰好产生本 witness 的一个新步骤，clause_index 为新 clause 的真实位置，premise_steps 引用已存在的真实步骤位置。

| 字符 | 新侧事实（先追加） | 追加规则 | 新 ground 根 | 规则步骤前提顺序 |
|---|---|---|---|---|
| C | 无 | `p{i-1}(?x,?y) -> p{i}(?x,?y)` | `p{i}(u,v)` | 原根 |
| I | 无 | `p{i-1}(?x,?y) -> p{i}(?y,?x)` | `p{i}(v,u)` | 原根 |
| J | `s{i}(v,e{i+1})` | `p{i-1}(?x,?y), s{i}(?y,?z) -> p{i}(?x,?z)` | `p{i}(u,e{i+1})` | 原根、新侧事实 |
| T | `s{i}(u,v)` | `p{i-1}(?x,?y), s{i}(?x,?y) -> p{i}(?x,?y)` | `p{i}(u,v)` | 原根、新侧事实 |

J 的 `e{i+1}` 是此前未出现的实体；缺号不补齐。C/I/T 不新建实体。`s{i}` 只在对应二前提步骤出现，不能复用以前的 side predicate。先保存原根步骤位置再追加侧事实，避免把侧事实误当为主前提。每个 clause／proof 保持追加顺序，最后一步的 conclusion 就是 query。

使用已有 `Atom`、`Clause`、`ProofStep`；clauses 和 proof 为 tuple。不靠 solver 自动生成 witness，不加入原推导的结论事实、干扰条款、常量规则、复用关系或循环。分支构造固定为“已有证明在第一个前提、另一前提是新事实”，不枚举其他树形。

手算锚点（编号是本 witness 中的 clause／proof 位置）：

```text
CJ:
0 [] -> p0(e0,e1)
1 p0(?x,?y) -> p1(?x,?y)
2 [] -> s2(e1,e3)
3 p1(?x,?y),s2(?y,?z) -> p2(?x,?z)
proof = [(0,(),p0(e0,e1)), (1,(0,),p1(e0,e1)),
         (2,(),s2(e1,e3)), (3,(1,2),p2(e0,e3))]
query = p2(e0,e3)

JC:
0 [] -> p0(e0,e1)
1 [] -> s1(e1,e2)
2 p0(?x,?y),s1(?y,?z) -> p1(?x,?z)
3 p1(?x,?y) -> p2(?x,?y)
proof premises = [(), (), (0,1), (2,)]
query = p2(e0,e2)
```

预期结果：80 个明确的 `(id, clauses, query, proof)`；每个二前提都保留两个实际发生。CJC 在 CJ 后追加 COPY，query 为 `p3(e0,e3)`，共有 5 步。`CC` 与 `II` 都以 `p2(e0,e1)` 为 query，但不能因端点相同而合并结构。

### 3. 用已验收接口测量目录与包含关系

四个预算固定且全部为真实 int `100_000`：C=`max_fact_checks`、D=`max_derivations`、S=`max_proof_steps`、O=`max_orientations`。它们是每次依赖调用的预算，不是本次审计的总运算预算。

直接按名导入下列公开 API，供测试在实际绑定处观察调用。对每个 candidate 依次完成：

- `canonical_motif_key(clauses, query, proof, max_steps=S, max_orientations=O)`：给定 witness 完整键，并通过其既有验证路径验证合法性。
- `count_canonical_proofs(clauses, query, max_fact_checks=C, max_derivations=D, max_proof_steps=S)`：实际规范证明数；不能将手写 witness 数量 1 当成枚举结果。
- `minimum_proof_depth(clauses, query, max_fact_checks=C, max_derivations=D)`：实际最短深度；不能用 ID 长度替代调用结果。

全部候选上述记录成功后，把所有原 `(clauses, query, proof)` 按目录顺序组成一次 references tuple。逐候选调用：

```python
heldout_motif_hits(
    clauses, (query,), references,
    max_fact_checks=C, max_derivations=D,
    max_proof_steps=S, max_orientations=O,
)
```

将唯一返回项中的 reference 位置映射为 ID，并按原目录顺序列出。边 `source -> target` 表示 source 的 query 全部有效证明中存在 target 的完整有根支持子树；包含自身。不能反转边，也不能从操作词前缀直接填报告，前缀仅是独立验收预期。

依赖异常原实例传播，不捕获为 0／空集合／未命中、不重试、不输出部分成功 JSON。允许 traceback 到 stderr。给定 witness 非法、其他 API 拒绝或预算不足时整次执行失败，保留原异常。无本层新增异常类或输入校验框架。

无需直接调用闭包 solver、重写证明枚举、规范键或匹配。T0018 每次重新验证整个目录是本版已知开销，80 次调用会有 6400 次参考键计算；不擅自改前置接口、缓存或改成只看给定 witness 的子树。此规模仅作离线参考审计，不声称可扩展生成性能。

### 4. 返回固定 schema 并通过模块入口输出 JSON

`audit_motif_candidates()` 无文件 IO，无 stdout 输出，返回新的普通 dict；嵌套容器只用普通 dict／list，叶为 str／int。真实完整 motif 键转成嵌套 list 仅用于 JSON 表示，保留所有版本标签和标量类型；比较和去重使用原 tuple 完整键，不使用哈希摘要、repr 或 ID 代替键。所有报告字段必须由本次构造或真实调用得到。

顶层字段固定为：

```text
schema_version = "motif_candidate_audit_v1"
candidate_family = "left_spine_ops_v1"
matching = "complete_rooted_support_subtree"
budgets = {max_fact_checks:100000, max_derivations:100000,
           max_proof_steps:100000, max_orientations:100000}
candidates = [CandidateRow, ...]        # 固定目录顺序
buckets = [BucketRow, ...]              # (depth, proof_steps) 升序
summary = {candidate_count, distinct_motif_count,
           containment_edges, proper_containment_edges}
```

`CandidateRow` 字段固定：`id, clauses, query, proof, motif_key, minimum_depth, canonical_proof_count, proof_steps, contained_ids`。`proof_steps` 为该 witness 步骤数，不是 C/D/S/O 或最短深度。对象序列化如下，不新增 ID／模板字段到 clause 或 Atom：

```text
Atom  -> {"pred": str, "args": [str, str]}
Clause -> {"body": [Atom, ...], "head": Atom}
ProofStep -> {"clause_index": int, "premise_steps": [int, ...], "conclusion": Atom}
```

`BucketRow` 固定为 `depth, proof_steps, candidate_count, distinct_motif_count`；按实际 depth 和 witness 步数分桶。候选数按行数计算，独立 motif 数按完整键集合计算。两类 edge count 分别统计全部 contained_ids 项数和其中 target ID 不等于 source ID 的项数。

`python -m kmesh.logic.motif_candidates` 在完整计算成功后输出一个 JSON 文档：UTF-8、`ensure_ascii=False, sort_keys=True, indent=2`、末尾一个换行。stdout 不夹进度／模型解释；不输出时间戳、耗时、绝对路径、环境信息或随机 run ID。两次成功运行应逐字节相同，运行时间等由控制器另行留证。不得在模块 import 时执行审计或输出报告，不新增 console script／文件格式解析 API。

预期结果：完整报告可用标准 `json.loads` 读取并据 witness 重建原逻辑对象，且保留离线审计与模型输入的边界。

### 5. 写真实行为测试，并对照手算完整性预期

以下是**待实测的预期**，不允许写死为观测字段：

| 最短深度 | witness 总步数（包含事实） | 候选数／独立完整键数 |
|---|---|---|
| 2 | 3 | 4／4 |
| 2 | 4 | 8／8 |
| 2 | 5 | 4／4 |
| 3 | 4 | 8／8 |
| 3 | 5 | 24／24 |
| 3 | 6 | 24／24 |
| 3 | 7 | 8／8 |

推导：设词长为 d，二前提字符数为 b，则步数是 `1+d+b`；每一步新增一个不同 head 谓词并只有一个已实例化支持，最短深度应为 d，规范计数应为 1。节点的 COPY／INV／JOIN／INTER schema 可区分，沿唯一非事实主分支逐级恢复操作词，因此不同词的完整键应不同。整个目录共 80 个不同完整键；这不等于全体深度 2–3 motifs。

包含关系预期：长度 2 的词只命中自身；长度 3 的词恰命中其前两个字符组成的词和自身。其它完整子树深度最多 1，不在目录里。故总边数 `16 + 64*2 = 144`，非自身边数 64，同深度没有不同 ID 之间的边。`CJC -> CJ`，但 `CJC` 不指向 `JC`；这也具体展示完整子树与上层裁剪片段的区别。

测试至少覆盖下列独立行为，不按测试条数验收：

- **构造锚点：** 在测试内独立手写 `CC, II, CJ, JC, CJC, JJ, TTT` 的完整 clauses/query/proof 或明确全文结构；至少 CJ、JC、CJC 比较全部序列与引用，覆盖字母方向、side predicate、fresh entity 和最后 query。不能导入 `reports/T0019/planning_probe.py` 或调用私有构造器生成 expected。
- **完整目录与真实 witness：** 精确检查 80 个 ID 及顺序；从 JSON 对象重建全部 witness，逐项通过既有独立 `verify_proof`，不得只检查最后一步。用已有 API 复核报告 key／证明数／深度；这些核验与手写锚点结合，不能只比较两次被测函数返回。可共享一次报告 fixture，避免每个断言重新跑整个审计。
